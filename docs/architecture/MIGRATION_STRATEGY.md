## ۲. منابع مهاجرت

| منبع | نحوه دسترسی |
|---|---|
| `data/meta.json` + `data/<col>/<id>.json` | خواندن مستقیم (درایور فایل) |

## ۳. مراحل مهاجرت

### مرحله ۱ — استخراج
- خواندن snapshot کامل (meta + docs + seq).
- گزارش: تعداد هر موجودیت، اسناد نامعتبر (JSON خراب، فیلدهای گمشده).

### مرحله ۲ — تجزیه meta
- `meta.users` → `users`
- `meta.cat.products` (۴۶ + ۸ آژانس) → `products`
- `meta.cat.materials` (۱۶) + `meta.cat.bom` → `materials`, `bom`
- `meta.suppliers` (۷) → `suppliers`
- `meta.lists` (۷ فهرست) → `lists`
- `meta.settings` (شامل vat، rate:3، discountCap) → `settings`

### مرحله ۳ — نرمال‌سازی تاریخ (Q-10، R-07)
- فیلدهای date-only (orders.sentAt، jobs.start/end، سررسید چک): تبدیل به `YYYY/MM/DD` ASCII (در صورت وجود ارقام فارسی).
- فیلدهای instant (created، updated، moves.t، next.t، hist[].t): timestamp UTC — بدون تغییر مقدار.
- گزارش فیلدهای غیرقابل تجزیه — **داده هرگز به‌صورت سکوت اصلاح نمی‌شود**.

### مرحله ۴ — نقشه‌گذاری موجودیت‌ها
- `accounts.phones` (آرایه) → جدول `account_phones`
- `accounts.contacts` → `account_contacts`
- `leads.hist` → `lead_hist`
- `leads.interest` → `lead_interest`
- `orders.items/pays/chques` → جداول جدا
- `moves` — مستقیم (هسته موجودی)
- `txns` — **در صورت تأیید** (Q-14) انتقال می‌یابد، در غیر این صورت از نو محاسبه می‌شوند.

### مرحله ۵ — اعتبارسنجی
- Zod schema‌های هدف روی داده موجود اجرا می‌شوند.
- گزارش خطاها (نه توقف) — تصمیم‌گیری دستی برای هر ردیف نامعتبر.
- بررسی ارجاعات (مثل `l.order` → سفارش موجود).

### مرحله ۶ — بارگذاری
- اسکریپت واحد با **تراکنش کامل** (fail-fast یا rollback).
- اجرای `nextSeq` معادل: ثبت آخرین شماره هر series (LD، PF، BY، PJ، TR).
- snapshot قبل/بعد برای بررسی.

### مرحله ۷ — صحه‌گذاری
- شمارش‌ها تطبیق می‌شوند (accounts ۲۳، leads ۲۹…).
- نمونه‌گیری ۱۰٪ داده — مقایسه میدانی.
- گزارش مدیر مالی (جمع مبالغ، تعداد چک‌ها).
