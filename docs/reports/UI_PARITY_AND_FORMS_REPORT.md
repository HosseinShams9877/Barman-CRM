## ۱. سایدبار: بازگشت به نسخه ساده بر اساس نقش

مرجع: `پلتفرم نهایی تیم بارمان/app/core.js`، بخش `navItems` و `ROLES`.

`src/components/layout/Sidebar.tsx` اکنون از `NAV_BY_ROLE` استفاده می‌کند. گروه «کارهای من»، نشان‌های تعداد و لینک‌های `?task=...` حذف شدند؛ هر مورد یک لینک مستقل با آیکن، برچسب و ترتیب نقش مربوط دارد. مسیر فعال با pathname، query و hash تشخیص داده می‌شود. باز و بسته شدن کشوی موبایل و Escape حفظ شده‌اند.

در بازبینی نهایی، عنوان‌های بلند باعث رشد عرض trackهای Grid و اسکرول افقی داخلی منو می‌شدند. trackها به `minmax(0, 1fr)` محدود شدند و عرض حداقل گروه/لینک صفر شد؛ عنوان بلند مانند Demo در عرض موجود کوتاه می‌شود. اسکرول افقی sidebar و nav بسته است و اسکرول عمودی حفظ شده است.

## ۴. خروج فوکوس فرم: علت، دامنه و آزمون

بازآفرینی اولیه در «کاربر جدید» قطعی بود: بعد از هر حرف، `document.activeElement` از input به پنل `dialog dialog-lg` می‌رفت. مشکل اصلی از remount input یا کتابخانه فرم نبود؛ effect مدیریت فوکوس در `Dialog` به `onClose` وابسته بود و callback inline در هر تغییر state فرم، effect را دوباره اجرا می‌کرد.

`Dialog.tsx` اکنون callback آخر را در ref نگه می‌دارد و چرخه باز شدن/فوکوس فقط به `open` و `embedded` وابسته است. Escape تنها دیالوگ بالایی را می‌بندد؛ Tab در همان دیالوگ محصور می‌شود؛ بعد از بسته شدن فوکوس به عنصر قبلی برمی‌گردد؛ قفل اسکرول با شمارنده دیالوگ‌های تو در تو مدیریت می‌شود.

`UserManager`، `ProductCatalog`، `MaterialCatalog` و `SuppliersPanel` الگوی آسیب‌پذیر state فرم و callback inline را داشتند و از اصلاح پایه بهره می‌برند. بازآفرینی پیش از اصلاح برای UserManager ثبت شده است؛ برای همه فرم‌های دیگر ادعای وجود همان خطا قبل از اصلاح نمی‌شود.

دو نقص مرتبط نیز اصلاح شدند: `BomEditor` هنگام رسیدن داده async انتخاب محصول/ردیف‌ها را ناپایدار می‌کرد؛ انتخاب پیش‌فرض و کلید هر ردیف پایدار شد. `JalaliDateInput` متن در حال تایپ را از مقدار استاندارد بیرونی جدا نگه می‌دارد تا دریافت مقدار جدید یا استانداردسازی تاریخ، متن/مکان تایپ را خراب نکند.

فرم‌های درخواستی بررسی شدند: `LeadFormDialog`، `AccountForm`، `OrderFormDialog`، `JobFormDialog`، `MoveFormDialog`، `UserManager`، `ProductCatalog`، `MaterialCatalog`، `SettingsPanel`، `ListsEditor`، `BomEditor` و `SuppliersPanel`. علاوه بر آن‌ها، فرم‌های تماس/از دست رفتن/ورود گروهی سرنخ، یازده مرحله سفارش و فرم‌های ثانویه، پرداخت، چک، برنامه پرداخت، لغو، QC، دریافت تولید، تأیید مالی خرید، تراکنش، فیلترها، جستجوی topbar و ورود بررسی شدند.

در Chrome برای **64 زمینه فرم، 209 فیلد تایپ‌پذیر، 1350 نویسه و 307 تغییر انتخاب/وضعیت** نتیجه ثبت شد. پس از **هر نویسه**، سه شرط کنترل شد: همان DOM node باقی بماند؛ activeElement همان input باشد؛ مقدار دقیقاً برابر پیشوند مورد انتظار باشد. متن فارسی «بارمان»، شماره کامل، تاریخ کامل، عدد چندرقمی، ایمیل و رمز متناسب با نوع فیلد تایپ شد. inputهای disabled/readOnly قابل تایپ نیستند و در شمارش تایپ نیامده‌اند. فرم‌های فقط انتخابی با select/radio/checkbox سنجیده شدند؛ برای selectها حداکثر چهار گزینه در هر کنترل آزموده شد.

## ۸. Blockers و موارد باز

هیچ مانع حل‌نشده‌ای برای اجرای شش دروازه یا پایداری فرم‌های آزموده‌شده باقی نمانده است. **درخواست تطبیق کامل همه پنل‌ها هنوز بسته نشده است.** موارد زیر دلیل توقف در مرز مدل/مجوز مستند یا کار بصری باقی‌مانده‌اند:

1. **رزرو موجودی Q-04:** گزارش فاز ۸ سطرهای ۱۲۲ و ۲۵۹، و گزارش فاز ۵ سطر ۳۴۷، پیاده‌سازی `o.resv` را معوق و `reservedQty` را صفر معرفی می‌کنند. ساخت عدد رزرو نمایشی یا اختراع منطق آزادسازی برای تقلید Demo انجام نشد.
2. **خرید محصول نمایندگی:** `docs/roadmap/PHASES/PHASE_06.md`، بخش مدل داده، `buy_items` را فقط با `materialId` تعریف کرده است. جریان محصول نمایندگی نیازمند توسعه قرارداد و مدل داده است.
3. **مجوز حرکت مواد و دریافت تولید:** طبق `AUTH_AND_PERMISSION_ARCHITECTURE.md`، `production.view` فقط برای management/admin/production و `inventory.moves` فقط برای management/admin/depot است. برای شبیه‌سازی Demo، دسترسی جدید به production/depot داده نشد.
4. **بانک چک خروجی و metadata مشتری/کاربر:** فاز ۶ برای `buy_cheques` بانک تعریف نکرده است؛ قرارداد مشتری شهر/ایمیل/شناسه ملی Demo را ندارد؛ کاربر رنگ شخصی ندارد. داده ساختگی در ستون‌ها یا فرم‌های بی‌قابلیت ذخیره اضافه نشد.
5. **کار بصری و تعامل باقی‌مانده بدون blocker فنی:** layout کامل مشتری/پرونده سفارش، wizard سرنخ، جزئیات کارت تولید، همه نمودارهای گزارش، بدهی تأمین‌کننده و رفتار جستجوی سراسری هنوز کامل نیستند. این‌ها صرفاً با سبز شدن تست‌ها تکمیل‌شده اعلام نمی‌شوند.

هیچ قانون کسب‌کاری، schema، migration، وابستگی یا تصمیم CD/Q برای پوشاندن این تفاوت‌ها تغییر نکرد. rule `noMoney` مطابق CD-31 در سرور تقویت شد. فهرست بالا باید مبنای دامنه بعدی تطبیق کامل قرار گیرد؛ در این اجرای مجاز، اصلاح‌های انجام‌شده و شواهدشان قابل بازبینی‌اند.
